# QMT LIVE 调度新鲜度与成交滑点

迁移任何会在 LIVE 中调度任务或调用交易函数的策略时使用本参考。

## 只补当天到期任务，不回放旧 K 线

QMT 行情服务在启动、准备、重启或重订阅时，可能把缓存中的最右侧 bar 推给 `handlebar`。`C.is_last_bar()` 返回 `True` 只表示最右侧，不保证这是今天或刚产生的实时 bar。

LIVE 入口采用失败关闭的四项守卫：

1. `C.is_last_bar()` 为真；
2. `get_bar_timetag(C.barpos)` 非 0 且可解析；
3. bar 日期等于本机当前日期；
4. 固定双向新鲜度窗口满足 `abs((runtime - bar_time).total_seconds()) <= 180`。

推荐把阈值集中声明为 `LIVE_FRESHNESS_SECONDS = 180`，但判断语义必须保持为绝对时间差、小于等于 180 秒。`runtime - bar_time` 在 `[-180, +180]` 内（含两端）通过；小于 `-180` 或大于 `+180` 都拒绝。不得改成 `0 <= delta <= 180`、按主图周期推导阈值或使用其他秒数。

任一项失败，立即返回，不构造交易上下文、不刷新目标、不调用账户/交易流水线。日志同时记录 `K线时间`、`runtime`、bar 日期和拒绝原因，并按原因节流。

系统时间仅用于 LIVE 新鲜度和事件诊断，不得参与 routine 到期判断，也不得替代日志前缀中的 K 线时间。初始化 timetag 为 0 时记录“无可用K线”，不能转换为 1970 年时间。

## LIVE 与 BACKTEST 共用简化的 handlebar 调度

默认只保留一套调度逻辑：

1. 在全局状态初始化 `g.executed_routines = set()`。
2. 每次 `handlebar` 从 `get_bar_timetag` 得到 `context.current_dt`；K 线日期改变时清空集合。
3. 每根 bar 按源策略注册顺序和业务依赖顺序扫描全部任务。
4. 若 `context.current_dt.strftime("%H:%M") < target_time`，跳过该任务。
5. 若任务名已在集合中，跳过；否则先加入集合，再调用 routine。

这使盘中启动后的第一根合格 bar 自然执行当天已经到期的任务，也使没有 09:00 主图 bar 的盘前任务在首根可用 bar 执行。不要为 LIVE 添加本机墙钟调度、`live_target_time`、精确分钟条件、`LIVE补运行` 特殊分支、独立交易日历缓存或负缓存。

内存任务集合只保证当前 Python 进程内不重复。启动或重连如果重建 Python 进程，当天已到期任务会再次执行；迁移报告必须披露该边界。涉及报单的任务还要检查最新账户/持仓、同方向未完成委托、目标仓位差额和运行期唯一订单键，避免重复报单。

在最终下单适配器再次调用新鲜度守卫。这样即使业务函数被其他回调或人工路径调用，旧 bar 也无法到达 `passorder`。

## 下单价格与成交关联

`passorder` 是异步且无返回值。调用未抛异常只表示“委托已报送”，不能写成“成交成功”。报单前保存：

- 小于 24 字符且运行期唯一的 `userOrderId`；
- 证券代码、买卖方向、请求数量；
- `latest_reference_price`，即紧邻 `passorder` 前通过 `get_full_tick` 确认的最新行情价格；
- 信号 K 线时间。

聚宽普通 `order` 系列默认是市价语义。QMT `prType=5` 是最新价限价，不能作为等价迁移。普通沪深股票/ETF 若采用共同的最优五档即成剩撤语义：

| 市场 | `prType` | `price` | 语义 |
|---|---:|---:|---|
| `.SH` | 42 | 0 | 最优五档即时成交，剩余撤销；0 使用涨跌停保护价 |
| `.SZ` | 47 | 0 | 最优五档即时成交，剩余撤销；0 使用涨跌停保护价 |

`latest_reference_price` 只用于衡量市价冲击，不是委托限价。日志明确记录 `order_type=market`、`market_pr_type`、保护价、`latest_reference_price` 和最终成交价。

调用 `C.set_account(account)` 启用 `order_callback`/`deal_callback`。官方把 `userOrderId` 放入 `Order/Deal.m_strRemark`；必须按 remark 关联，不能只按代码关联同日多笔委托。`userOrderId` 必须小于 24 字符且运行期唯一；计数型 ID 达到长度允许的最大序号时必须拒绝新单，不能通过 `%` 取模、截断或重启计数复用。

## 市价买入的保护价、验资与跨日缓存

`price=0` 的沪深市价买入由 QMT 使用当日涨停价作为保护限价，柜台也据此验资。迁移实现遵循以下固定流程：

1. 把 `InstrumentName` 等静态元数据与 `UpStopPrice`、`DownStopPrice` 等交易日动态字段分开缓存；K 线日期变化时清空动态详情缓存。
2. LIVE 计算买入数量前，以完整详情模式强制刷新当日 `UpStopPrice`。刷新失败时失败关闭，不得沿用缓存保护价报单。
3. 最终调用 `passorder` 前再次刷新保护价和可用资金；若涨停价上调导致原数量无法通过验资，按费用口径向下缩量到最小交易单位。
4. 日志记录原保护价、新保护价、原数量、最终数量、可用资金和所需资金；所有日志仍通过 `qmt_log` 并带 K 线时间。
5. 零成交废单原因含“资金不足”或 `insufficient funds` 时，清除该代码的动态详情缓存，释放对应信号键，并记录一次减量重试状态。
6. 下一次重试重新读取当日保护价、最新可用资金并重算数量，在可买数量基础上至少再减少一个最小交易单位。禁止以相同保护价、相同数量机械重报。

成交回报读取：

| 含义 | Deal 字段 |
|---|---|
| 关联键 | `m_strRemark` |
| 成交编号 | `m_strTradeID` |
| 成交价格 | `m_dPrice` |
| 成交数量 | `m_nVolume` |
| 成交金额 | `m_dTradeAmount` |

按 `(remark, trade_id)` 去重。部分成交累计 `sum(price * volume)` 与 `sum(volume)`，最终成交价为二者相除。除主推外，每根新 bar 对仍在途的追踪记录查询一次 `DEAL` 对账，防止回调遗漏；委托终态用 `order_callback` 识别全成、部分成交后撤单、废单和零成交撤单。

## 滑点定义

统一让正数表示对策略不利：

```text
买入绝对滑点 = final_deal_price - latest_reference_price
卖出绝对滑点 = latest_reference_price - final_deal_price
滑点比例 = 绝对滑点 / latest_reference_price
滑点基点 = 滑点比例 * 10000
```

每笔成交日志记录本次成交价/数量、累计数量和累计加权均价；全部成交或委托终止时记录参考价、最终成交价、实际成交数量、绝对滑点、比例、基点和终止原因。部分成交后撤单只对实际成交部分计算。

## 最小验收矩阵

1. 周一盘前收到上周五最右 bar：不进入任何任务、不查询账户、不报单。
2. 盘前收到当天未来标签 bar：领先运行时不超过 180 秒可通过时间差项，超过 180 秒拒绝；其余守卫仍须全部通过。
3. 同日缓存 bar：落后运行时不超过 180 秒可通过时间差项，超过 180 秒不调度、不报单；精确 `-180/+180` 秒边界应通过。
4. 14:05 的 bar 只按顺序执行 09:00、09:40、14:01 三个已到期任务；14:06 和 14:09 不提前。
5. 14:07 的 bar 只新增执行 14:06 任务；14:10 的 bar 只新增执行 14:09 任务；重复 bar 不重复执行。
6. K 线日期变化时清空当日任务集合；进程重启后已到期任务重新执行的边界已披露。
7. 下单适配器直接收到旧上下文时仍拒绝 `passorder`。
8. 两笔部分成交得到正确的成交量加权均价，重复 trade ID 不重复累计。
9. 买入高价成交和卖出低价成交均产生正滑点；价格改善产生负滑点。
10. 部分成交后撤单输出实际成交部分最终统计，零成交废单不伪造成交价。
11. 沪市报单参数为 `(42, 0)`、深市为 `(47, 0)`，不存在 `prType=5` 最新价限价报单。
12. 委托与终态日志同时包含 `latest_reference_price`、成交量加权 `final_deal_price` 和两者滑点。
13. 进程跨交易日运行后，旧日 `UpStopPrice` 不参与新日买入数量计算；最终报单前强制刷新当日保护价，资金不够时自动缩量。
14. 零成交资金不足废单会清除动态缓存并释放信号键；允许的下一次重试重新定价、重新验资并至少减少一手，不会原数量重复报单。
